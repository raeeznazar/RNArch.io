JavaScript Closures

A closure is created when a function remembers and can access variables from its outer lexical scope, even after the outer function has finished executing. It's one of the most asked JavaScript interview topics, and it's behind every event handler and hook you write in React Native.

02

What is a closure?

Start with the simplest example:

counter.js 
function outer() {
  let count = 0;

  function inner() {
    count++;
    console.log(count);
  }

  return inner;
}

const counter = outer();

counter(); // 1
counter(); // 2
counter(); // 3

When const counter = outer(); runs, outer() finishes executing. You might expect its local variable count to be destroyed. That's not what happens:

Because inner() still references count, JavaScript keeps that lexical environment available. Every call to counter() reaches the same count, so it prints 1, 2, 3. We say inner has closed over count.

🎒

Why is it called a closure?

Think of the function as carrying a backpack. When inner is created, it packs a link to the variables around it (count) and takes that backpack wherever it goes, even after outer is long gone. The function plus its backpack is the closure.

⚠️

It's a live link, not a copy

A closure doesn't save the value of count. It keeps the variable itself. If the variable changes, the function sees the new value. This one detail explains the warm-up puzzle and stale closures in React.

04

Each call gets its own closure

A very common interview follow-up:

create-counter.js 
function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const counter1 = createCounter();
const counter2 = createCounter();

console.log(counter1()); // 1
console.log(counter1()); // 2
console.log(counter1()); // 3

console.log(counter2()); // 1

Why does counter2() start from 1? Because each call to createCounter() creates a new lexical environment with a fresh count = 0. counter1 and counter2 don't share it.

05

Closures give you private variables

This is one of the most useful practical applications. The only way to reach balance is through the functions that closed over it.

bank-account.js 
function createBankAccount() {
  let balance = 1000;

  return {
    getBalance() {
      return balance;
    },

    deposit(amount) {
      balance += amount;
    }
  };
}

const account = createBankAccount();

account.deposit(500);

console.log(account.getBalance()); // 1500
console.log(account.balance);      // undefined

account.balance is undefined because balance is a variable in the closure, not a property of the returned object. This is encapsulation without classes.

Setting account.balance = 0 just adds a new, unrelated property to the object. The real balance inside the closure is untouched.

06

Closures and timers

Another very common interview question:

timeout.js 
function test() {
  let name = "John";

  setTimeout(() => {
    console.log(name);
  }, 1000);
}

test(); // after 1 second: John

test() finishes immediately, but one second later John is still printed. The callback () => { console.log(name); } forms a closure over name. Step through the setTimeout example in the visualizer to watch it.

The loop trap (the warm-up puzzle)

With var, the loop has one i. All three callbacks close over that same variable, and they only run after the loop has finished and set it to 3. With let, every iteration gets its own i, so each callback closes over a different variable.

Loop variableHow many i variables?Prints
for (var i = 0; ...)One, shared by the whole loop3 3 3
for (let i = 0; ...)A new one per iteration0 1 2
loop-fixed.js 
// Fix 1: use let
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100); // 0 1 2
}

// Fix 2 (pre-ES6): create a new scope with a function
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j), 100); // 0 1 2
  })(i);
}
07

Closures in React and React Native

The closure mechanism is plain JavaScript. It isn't a React Native feature and has nothing to do with the native architecture. React and React Native simply run on top of it, then render to different places.

An event handler is a closure

Counter.tsx 
function Counter() {
  const [count, setCount] = useState(0);

  const handlePress = () => {
    console.log(count);
  };

  return (
    <Button
      title="Count"
      onPress={handlePress}
    />
  );
}

handlePress is a closure. It remembers the count variable from the render in which handlePress was created.

The same thing in a typical screen:

ProfileScreen.tsx 
function ProfileScreen() {
  const [name, setName] = useState("John");

  const handlePress = () => {
    console.log(name);
  };

  return (
    <>
      <Text>{name}</Text>
      <Button title="Print Name" onPress={handlePress} />
    </>
  );
}

Each render has its own closure

This is the part interviewers want you to understand. A function component is just a function. Every render calls it again, which creates a new lexical environment with that render's count, and a brand-new handlePress that closes over it.

Where you meet closures in a component

Event handlers

An onPress arrow function closes over props like id.

Effects

The useEffect callback sees the state from the render that created it.

Memoized callbacks

useCallback keeps one closure until its dependencies change.

Custom hooks

Hooks return functions that close over the hook's state and refs.

08

Stale closures

Because each render has its own closure, a callback that lives longer than its render (a timer, an interval, a subscription, a memoized function) keeps seeing that render's values. This is a very common interview question.

Counter.tsx 
function Counter() {
  const [count, setCount] = useState(0);

  const handlePress = () => {
    setTimeout(() => {
      console.log(count);
    }, 3000);
  };

  return (
    <>
      <Text>{count}</Text>
      <Button title="Start" onPress={handlePress} />
      <Button title="Increment" onPress={() => setCount(c => c + 1)} />
    </>
  );
}

Why? The callback () => { console.log(count); } closed over the count from the render where Start was pressed. It doesn't automatically look up the latest state. That's a stale closure.

How do you fix stale closures?

There are several approaches, depending on the situation.

Fix 1: functional state update

If you're updating state based on the previous state, let React hand you the latest value:

functional-update.ts 
setCount(prev => prev + 1); // ✅ always based on the latest value
setCount(count + 1);       // ⚠️ uses this render's count

This is safer, especially when multiple updates are queued or when the update happens inside a long-lived callback like an interval:

Ticker.tsx 
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);    // ❌ count is always 0: stuck at 1
    setCount(c => c + 1);   // ✅ keeps counting
  }, 1000);
  return () => clearInterval(id);
}, []);

Fix 2: useRef for the latest value

If you need to read the latest value inside a long-lived callback:

latest-ref.ts 
const countRef = useRef(count);

useEffect(() => {
  countRef.current = count;
}, [count]);

setTimeout(() => {
  console.log(countRef.current); // latest value
}, 3000);

The closure still captures something old, but what it captures is the ref object, which is the same object on every render. Its .current property is updated, so reading it gives the latest value.

Fix 3: correct dependencies in useEffect

❌ stale
useEffect(() => {
  console.log(count);
}, []);
✅ fresh
useEffect(() => {
  console.log(count);
}, [count]);

With [], the effect runs once and captures count = 0 from the initial render. It never runs again when count changes, so it only ever sees 0. With [count], React runs a new effect (with a new closure) every time count changes.

Fix 4: correct dependencies in useCallback

❌ stale
const handlePress = useCallback(() => {
  console.log(count);
}, []);
✅ fresh
const handlePress = useCallback(() => {
  console.log(count);
}, [count]);

The dependency [count] tells React: "this callback depends on count; give me an updated callback when count changes." Without it, useCallback keeps returning the closure from the first render, which captured the initial value.

10

The interview answer

Closure in one sentence (memorize this)

"A closure is a function together with its surrounding lexical environment, allowing the function to access variables from its outer scope even after the outer function has finished execution."

"Where do you use closures?"

"Closures are commonly used for data encapsulation and private state, callbacks, event handlers, timers, function factories, memoization, and asynchronous JavaScript. In React and React Native, closures are especially common in event handlers, effects, callbacks, and hooks."

"How does closure work in React Native?"

"Closures in React Native work the same way as normal JavaScript closures. Functional React components create new lexical environments on each render, and event handlers, effects and callbacks can capture values from the render in which they were created. This can lead to stale closures when a callback retains an older state or prop value."

⚠️

Don't explain closures as a native architecture feature (Bridge, JSI, Fabric). They're pure JavaScript. Follow up with how you fix stale closures: functional updates, useRef, and correct dependency arrays.

Bonus points in an interview

Mention that closures hold a live reference (not a copy), that every call creates a new closure, and that closures keep memory alive, so a forgotten listener or interval can cause a memory leak. Then give the stale-closure example from React Native.
