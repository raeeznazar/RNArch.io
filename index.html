React Native Architecture

How JavaScript talks to native Android and iOS, why the old Bridge was replaced, and what JSI, Fabric, TurboModules and Codegen each do. Written for interview preparation.

~12 min read Bridge → JSI Interview ready
01

Overview

React Native lets us build native mobile applications using JavaScript/TypeScript and React. The JavaScript code runs inside a JavaScript engine (Hermes by default), and React Native connects that code to native Android and iOS functionality.

Unlike React for the web, which renders HTML elements, React Native renders real native UI components. A <View> becomes an Android ViewGroup or an iOS UIView.

02

Old architecture: the Bridge

The old architecture was built around a single component: the Bridge. Every interaction between JavaScript and native code had to cross it.

The Bridge used asynchronous, serialized communication. Data had to be converted into JSON-like messages before crossing the boundary and parsed again on the other side.

Why was the Bridge a problem?

Imagine calling a native module with a small object:

JavaScript 
NativeModule.doSomething({
  userId: 123,
  name: "John",
});

Even this simple call has to travel through several steps:

One call is cheap. Thousands of calls per second are not. The cost becomes noticeable with:

  • animations
  • gestures
  • large lists
  • high-frequency events (scroll, sensors)
  • complex native modules
  • large amounts of data crossing the JS/native boundary
⚠️

Key limitation

Because everything was asynchronous and serialized, JavaScript could never call native code synchronously, and a busy Bridge meant dropped frames. The Bridge became one of the biggest architectural bottlenecks.

03

The New Architecture

The New Architecture was introduced to remove these limitations. It is enabled by default since React Native 0.76. It rests on four technologies:

Foundation
JSI

A direct interface between JavaScript and C++/native code. No serialization.

Rendering
Fabric

The new rendering system that coordinates React with native UI.

Native modules
TurboModules

The new native module system, built on JSI and loaded lazily.

Type safety
Codegen

Generates type-safe native interfaces from TypeScript specs.

💡

Remember this for your interview

JSI is the foundation, Fabric is the new rendering system, TurboModules are the new native module system, and Codegen provides type-safe native interfaces.

04

JSI: JavaScript Interface

JSI is a lightweight C++ API that lets JavaScript interact directly with C++ and native code, without relying on the old asynchronous Bridge.

With JSI, JavaScript can hold references to C++ objects and call their methods directly. This gives us:

  • No serialization overhead: data is not converted to JSON to cross the boundary.
  • Synchronous calls when needed, as well as asynchronous ones.
  • Engine independence: JSI is an abstraction, so React Native can run on Hermes, JavaScriptCore, or other engines.
05

Fabric

Fabric is React Native's new rendering system. It is responsible for coordinating React's rendering with native UI.

Because the shadow tree now lives in shared C++ and is reached through JSI, Fabric brings improvements in:

  • rendering performance
  • responsiveness
  • support for concurrent React features (e.g. startTransition, Suspense)
  • synchronous layout and rendering where appropriate
  • better interoperability with native components
06

TurboModules

TurboModules replace the older Native Modules system. Native modules are how JavaScript reaches platform capabilities such as:

GPS Camera Bluetooth Secure Storage File System

The big win: lazy loading

In the old system, every native module was initialized at app startup, whether it was used or not. TurboModules are loaded only when they are first needed.

Old Native Modules TurboModules
At startup App starts → load all 100 modules App starts → load nothing extra
On first use Already loaded Module is loaded on demand
Result Slower startup, more memory Faster startup, less memory
07

Codegen

Codegen generates the native "glue" code from a typed JavaScript/TypeScript specification, so the JS side and native side always agree on the interface.

You describe the module once in TypeScript:

NativeStorage.ts 
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  getItem(key: string): Promise<string>;
  setItem(key: string, value: string): Promise<void>;
}

// Codegen reads this spec and generates the native interfaces
export default TurboModuleRegistry.getEnforcing<Spec>('NativeStorage');

This gives:

  • Type safety: type mismatches are caught at build time, not as runtime crashes.
  • Consistency: less hand-written, error-prone boilerplate on each platform.
  • Predictable JS ↔ Native communication.

Performance

Why can React Native apps become slow?

Performance problems usually come from one of these:

  • too much work on the JavaScript thread
  • excessive JS ↔ native interactions
  • unnecessary re-renders
  • large lists rendered inefficiently
  • expensive calculations during render
  • poorly optimized images

How do you optimize React Native?

Know these three areas for interviews.

1. React optimization

  • React.memo: skip re-rendering a component when its props haven't changed.
  • useMemo: cache the result of an expensive calculation.
  • useCallback: keep a function reference stable between renders.
  • Avoid unnecessary state and keep state as close to where it's used as possible.
  • Avoid unnecessary re-renders; profile with React DevTools.

2. Lists

Use FlatList (virtualized, renders only what's on screen) instead of ScrollView (renders everything at once) for large datasets.

OptimizedList.tsx 
<FlatList
  data={items}
  renderItem={renderItem}                  // memoized with useCallback
  ={(item) => item.id.toString()} // stable, unique keys
  ={(_, index) => ({          // skip measuring fixed-height rows
    length: ITEM_HEIGHT,
    offset: ITEM_HEIGHT * index,
    index,
  })}
  ={10}                  // items in the first render
  ={10}                 // items rendered per batch
  ={5}                           // screens of content kept mounted
/>

Tip: click a highlighted prop to see a full explanation.

The easiest way to remember all 5

Think about a restaurant. You have 10,000 customers but only need to serve the ones around you.

Interview answer: "How would you optimize a FlatList?"

"First, I would make sure every item has a stable keyExtractor. If the item height is fixed, I'd use getItemLayout so FlatList doesn't need to measure every item. Then I'd tune initialNumToRender, maxToRenderPerBatch, and windowSize based on the item complexity and device performance. I would also avoid unnecessary re-renders using React.memo, keep renderItem stable where appropriate, and avoid putting expensive calculations inside renderItem."

3. Images

  • Serve appropriately sized images, not full-resolution originals.
  • Cache images.
  • Use compressed assets (e.g. WebP).
  • Use an optimized image library (such as expo-image) when needed.
10

One-minute interview answer

If you're asked to "explain React Native's architecture", this covers everything in about a minute:

React Native allows us to build native Android and iOS applications using React and JavaScript or TypeScript. Our React code runs in a JavaScript runtime, while the actual UI and platform-specific functionality are handled by native Android and iOS code.

Historically, React Native used a Bridge for communication between JavaScript and native code. The Bridge serialized messages and communicated asynchronously, which could become a bottleneck for high-frequency communication.

The New Architecture addresses this with JSI, Fabric, TurboModules and Codegen. JSI provides a more direct interface between JavaScript and native or C++ code. Fabric is the new rendering system, while TurboModules are the newer native module system and support things such as lazy loading. Codegen generates type-safe native interfaces from specifications.

So, at a high level, React handles the application and component logic, JSI provides the JavaScript-to-native interface, Fabric handles rendering, TurboModules provide native functionality, and Android or iOS ultimately renders and executes the native functionality.
