JavaScript Execution Context

03

What is an execution context?

Every time JavaScript runs some code, it first sets up an environment for it. That environment holds everything the code needs: which variables exist, what their values are, what this means, and where to look if a variable isn't found locally.

There are two main kinds:

  • The Global Execution Context is created once, when your script starts.
  • A Function Execution Context is created every single time a function is called. Call the same function three times and you get three separate contexts, each with its own fresh variables.
🍳

Think of a kitchen

Before cooking a recipe, a chef clears a counter, lays out labelled bowls for every ingredient (still empty), and only then starts cooking. The counter is the execution context. The empty labelled bowls are the creation phase. Cooking is the execution phase.

What's inside a context

Memory

Variables and functions declared in this code. Also called the variable environment.

Code thread

Runs the code one line at a time, top to bottom. JavaScript has only one thread.

this

A value decided when the context is created, based on how the function was called.

Outer reference

A link to the context where this code was written. Used to find variables that aren't local.

04

Every context goes through two phases

This is the single most useful thing to understand. JavaScript does not simply read your file and run it. It reads it twice, in a sense.

1. Creation phase

The engine scans the code for declarations and reserves memory for them. No code runs yet, and no values are assigned. It also sets up this and the outer reference.

2. Execution phase

Now the code runs line by line. Assignments fill in the real values, functions get called, and output is produced.

"Hoisting" doesn't mean code physically moves to the top. It means memory was set aside during the creation phase, before any line ran.

05

The call stack keeps track of which context is running

JavaScript can only do one thing at a time, so it needs to remember where it is. It uses a stack, like a pile of plates: the last one added is the first one removed.

Local variables are discarded on return unless a closure holds on to them (see Closures).

⚠️

Stack overflow

If a function keeps calling itself without stopping, contexts pile up until the engine runs out of room. That's the Maximum call stack size exceeded error.

06

The scope chain decides where variables are found

When code uses a variable, JavaScript looks in the current context's memory first. If it isn't there, it follows the outer reference to the next context, and keeps going until it reaches Global. If it's still not found, you get a ReferenceError.

The important part: the outer reference points to where the function was written, not where it was called. This is called lexical scope. Try the "Scope chain" example in the visualizer and watch the dashed outlines trace the lookup.

07

Closures: a function keeps its birthplace's memory

Normally a function's variables disappear when its context is popped off the stack. But if an inner function that uses those variables survives (for example, because it was returned), JavaScript keeps those variables alive for it. That saved memory is the closure.

This is how counters, private variables, event handlers and React hooks like useState remember values between calls. The "Closure" example in the visualizer shows the saved memory sitting outside the stack.

Closures get their own lesson, with private state, timers, the loop trap and stale closures in React Native: JavaScript Closures.

Quick summary

JavaScript creates a context, fills its memory in the creation phase, runs the code in the execution phase, pushes a new context for every function call, pops it on return, and looks up variables through the chain of places the code was written.
