SSL/TLS & App Security

In React and React Native interviews, SSL comes up under API security, HTTPS, certificates, token storage and network security. The key is knowing what TLS protects, what it doesn't, and when pinning is worth its cost.

~20 min Eavesdropper demo Certificate & pinning checker 6-question quiz
01

Warm-up puzzle

A classic interview trick question.

login.ts
// All API calls use https://
const { token } = await login("https://api.example.com/login");

await AsyncStorage.setItem("token", token);
The app uses HTTPS everywhere. Is the token stored securely?

02

What is SSL / TLS?

SSL (Secure Sockets Layer) is the older protocol for securing communication between a client and a server. It's deprecated. Today, TLS (Transport Layer Security, versions 1.2 and 1.3) is what's actually used. People still say "SSL" when they mean HTTPS/TLS.

The three goals

🔐 Encryption

Others shouldn't be able to read the data.

🪪 Authentication

The client can verify it's talking to the legitimate server.

🧾 Integrity

Data can't be modified in transit without it being detected.

03

HTTP vs HTTPS

HTTPS = HTTP + TLS. The HTTP request is the same; TLS wraps it in an encrypted, authenticated channel.

05

          
Certificates and Certificate Authorities

          
A certificate is how the server proves its identity. It contains:


          

            
Domain
Which hostnames it's valid for, e.g. api.example.com.

            
Public key
The server's key, used during the handshake.

            
Issuer & validity
Which CA issued it, and its not-before / not-after dates.

            
Signature
The CA's digital signature, so it can't be forged or edited.

          


          

            A Certificate Authority (CA) is a trusted
            organization that issues and signs certificates, for example
            Let's Encrypt, DigiCert or GlobalSign. Your device ships with a set
            of trusted root certificates, and trust flows down a chain:
          


          

          
When the client must reject the connection

          

            

              
                
ProblemExample

              
              
                
Hostname mismatchApp calls api.example.com, certificate is for otherdomain.com

                
Expired certificateThe not-after date has passed

                
Untrusted certificateSelf-signed, or issued by a CA the device doesn't trust

                
Invalid chainA missing intermediate, or a signature that doesn't verify

06

          
SSL pinning

          

            This is probably the most React Native-specific security topic.
            Normally the app accepts any valid certificate from
            any CA the device trusts. With certificate or public-key
            pinning, the app also expects a specific
            certificate or public key.
          


          

          
Why pin?

          

            Imagine an attacker manages to get a certificate the device trusts:
            a compromised CA, or a rogue CA installed on a rooted or managed
            device. Normal validation passes, and the connection is accepted.
            Pinning asks one more question, "is this the key I expect?", and
            rejects the impostor. That's stronger assurance of the server's
            identity against certain man-in-the-middle attacks.

    07
    
          
    Is SSL pinning always necessary?
    
          
    
            No. This is an important senior-level answer.
            Pinning adds operational complexity, because certificates expire
            and get replaced:
          
    

          

          
    
            
    
              
                
    What you pinSurvives a certificate renewal?Notes
    
                  
              
                
    The exact certificateNoBreaks on every renewal (Let's Encrypt renews every ~90 days)
    
                
    The public key (SPKI hash)Yes, if the key pair is keptThe usual choice
    
                
    Public key + backup pinsYes, even when rotating keysKeep a backup key offline and ship its pin in advance
    
                  
            
    
          
    

          
    On Android, pins can be declared in the Network Security Config, with backup pins and an expiry date:
    
          
    
            
    
              android/app/src/main/res/xml/network_security_config.xml
            
    
            
    <network-security-config>
  <domain-config>
    <domain includeSubdomains="true">api.example.com</domain>
    <pin-set expiration="2027-01-01">
      <pin digest="SHA-256">base64-of-current-public-key=</pin>
      <pin digest="SHA-256">base64-of-backup-public-key=</pin>
    </pin-set>
  </domain-config>
</network-security-config>
    
          
    
          
    
            On iOS, pinning is usually done with a library such as TrustKit or
            a React Native pinning library that configures both platforms.
          
    

          
    
            
    
              
    ❌
    
              
    
                
    Don't say
    
                
    "Every React Native app must use SSL pinning."
    
              
    
            
    
            
    
              
    ✅
    
              
    
                
    Say
    
                
    
                  "HTTPS/TLS should be standard for network communication.
                  Certificate or public-key pinning can provide additional
                  protection for higher-risk applications, but it introduces
                  certificate rotation and maintenance considerations."
                
    
              
    
            
    
          
    
        
    

        
        
    
          
    08
    
          
    HTTPS doesn't protect data stored on the phone
    
          
    
            HTTPS protects data while it travels. Once a token
            arrives and you save it, storage is a separate security concern:
          
    

          
    
            
    NetworkHTTPS / TLS
    
            
    StorageKeychain / Keystore
    
            
    Authenticationwho you are
    
            
    Authorizationwhat you may do
    
          
    

          
    React Native token storage
    
          
    
            For sensitive tokens, don't casually say "I'll store it in
            AsyncStorage." AsyncStorage is ordinary, unencrypted app storage.
            Platform-backed secure storage is generally preferable.
          
    

          
    
            
    
              
                
    StorageEncrypted?Use it for
    
                  
              
                
    AsyncStorage / MMKV (default)NoPreferences, cache, non-sensitive state
    
                
    expo-secure-store, react-native-keychainYes, backed by iOS Keychain / Android KeystoreAccess and refresh tokens, credentials
    
                
    Hardcoded in the JS bundleNo, extractableNever for secrets
    
                  
            
    
          
    

          

          
    
            
    
              
    ❌ plain storage
    
              
    await AsyncStorage.setItem(
  "token",
  token
);
    
            
    
            
    
              
    ✅ secure storage (Expo)
    
              
    import * as SecureStore from "expo-secure-store";

await SecureStore.setItemAsync("token", token);
    
            
    
          
    
          
    The exact implementation depends on the platform and the library.
    
        
    

        
        
    
          
    09
    
          
    SSL/TLS vs JWT: don't confuse them
    

          

          
    
            They solve different problems and usually work together:
            HTTPS/TLS + an authentication token + secure token
            storage. A JWT sent over plain HTTP could be stolen; TLS
            without a token doesn't tell the server who the user is.
          
    
        
    

        
        
    
          
    10
    
          
    React Native security architecture
    

          

          
    Never ship secrets in the app
    
          
    
            Anything in the JavaScript bundle or the app binary can be
            extracted by anyone who downloads the app, including values from
            .env files that get inlined at build time.
          
    
          
    
            
    
              config.ts
            
    
            
    const STRIPE_SECRET_KEY = "sk_live_...";   // ❌ extractable from the bundle
const DB_PASSWORD = "...";               // ❌ never on the client

// ✅ The app calls your API; your server holds the secret
await fetch("https://api.example.com/payments", {
  method: "POST",
  headers: { Authorization: `Bearer ${accessToken}` },
});
    
          
    

          
    
            
    🚫
    
            
    
              
    
                Never put real API secrets, private keys, database
                credentials, or other server-side secrets inside the mobile
                app. Obfuscation only slows attackers down.
              
    
            
    
          
    
        
    

        
        
    
          
    11
    
          
    Interview answers
    
          
    Answer each one out loud, then reveal it.
    
          
          
    

          
    ⭐ "How do you secure a React Native application?"
    
          
    
            
    
              "I would start with HTTPS/TLS for all API communication. For
              authentication, I would use short-lived access tokens and
              appropriate refresh-token handling, and store sensitive tokens
              using platform-backed secure storage rather than ordinary
              storage. On the server, I'd enforce authentication and
              authorization, validate inputs and implement rate limiting. For
              high-security applications, I would also consider certificate or
              public-key pinning, while having a proper certificate rotation
              strategy. I would also avoid hardcoding secrets in the React
              Native bundle, because anything shipped to the client should be
              considered potentially extractable."
            
    
          
    

          
    
            
    🎯
    
            
    
              
    
                That last sentence is the one that stands out in a React Native
                interview. It shows you understand that the client is never a
                safe place for secrets.
