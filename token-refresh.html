Axios Token Refresh

"How do you handle access-token expiration and refresh tokens in Axios?" If you've worked with Axios in React or React Native, expect this question. Here's the full flow, from the request interceptor to the refresh queue that handles many 401s at once.

Basic authentication flow

When the user logs in, the server returns two tokens:

POST /auth/login → response 
{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ..."
}

You store them securely. Then every API request sends the access token in a header:

HTTP header
Authorization: Bearer ACCESS_TOKEN
03

The request interceptor

Instead of adding the header by hand in every call:

❌ repeated in every call 
axios.get("/users", {
  headers: {
    Authorization: `Bearer ${accessToken}`
  }
});

you create an Axios instance and attach the token once, in a request interceptor:

✅ api.ts 
const api = axios.create({
  baseURL: API_URL,
});

api.interceptors.request.use(async (config) => {
  const token = await getAccessToken();

  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  return config;
});

Now every request automatically gets the token:

06

The hard part: many requests at once

This is where interviewers test you. The access token expires, and at the same time:

simultaneous requests
GET /users       → 401
GET /profile     → 401
GET /orders      → 401
GET /dashboard   → 401

This is often called a refresh queue or single-flight refresh pattern. It needs two pieces of state:

isRefreshing

false until the first 401. That request sets it to true and starts the refresh. Every later 401 sees true and waits instead of refreshing.

failedQueue

The waiting requests. When the refresh succeeds, the queue is processed: every request is retried with the new token.

What you should see:

  • Naive: 4 requests → 4 refresh calls. Everything eventually works, but three refreshes were wasted.
  • Refresh queue: the first 401 refreshes; the other three show queued and retry with the same new token. 1 refresh call.
  • Refresh token expired: the refresh fails, the queued requests are rejected, and the user is logged out. With the naive interceptor, logout runs four times.
08

The Axios implementation

Here's the pattern to understand for an interview. You don't need to memorize every line: understand the architecture.

refreshQueue.ts 
let isRefreshing = false;
let failedQueue = [];

const processQueue = (error, token = null) => {
  failedQueue.forEach(({ resolve, reject }) => {
    if (error) {
      reject(error);
    } else {
      resolve(token);
    }
  });

  failedQueue = [];
};

The response interceptor:

api.ts 
api.interceptors.response.use(
  response => response,

  async error => {
    const originalRequest = error.config;

    // 1. Only handle 401s
    if (error.response?.status !== 401) {
      return Promise.reject(error);
    }

    // 2. Already retried once? Don't loop
    if (originalRequest._retry) {
      return Promise.reject(error);
    }

    originalRequest._retry = true;

    // 3. A refresh is already running: wait in the queue
    if (isRefreshing) {
      return new Promise((resolve, reject) => {
        failedQueue.push({
          resolve,
          reject
        });
      }).then(token => {
        originalRequest.headers.Authorization =
          `Bearer ${token}`;

        return api(originalRequest);
      });
    }

    // 4. First 401: this request does the refresh
    isRefreshing = true;

    try {
      const newToken = await refreshAccessToken();

      processQueue(null, newToken);

      originalRequest.headers.Authorization =
        `Bearer ${newToken}`;

      return api(originalRequest);

    } catch (refreshError) {

      processQueue(refreshError);

      // logout user

      return Promise.reject(refreshError);

    } finally {
      isRefreshing = false;
    }
  }
);
💡

Call the refresh endpoint without the interceptor

Make refreshAccessToken() use plain axios or a separate instance, not api. Otherwise a 401 from /auth/refresh itself goes back through this interceptor, which is waiting on that very refresh.

🔁

A shorter variant: share the refresh promise

Instead of a flag plus a queue, you can store the in-flight refresh as a promise, e.g. refreshPromise ??= refreshAccessToken(). Every 401 awaits the same promise, and you clear it when it settles. Same single-flight idea.

Storing tokens in React Native

With React Native or Expo, a common setup is:

TokenWhereWhy
Access tokenMemory and/or secure storageShort-lived, read on every request
Refresh tokenSecure storageLong-lived: whoever has it can get new access tokens

For example, Expo provides SecureStore:

tokens.ts 
import * as SecureStore from "expo-secure-store";

await SecureStore.setItemAsync("refreshToken", refreshToken);
const token = await SecureStore.getItemAsync("refreshToken");
⚠️

AsyncStorage is not encrypted, so don't keep tokens there. SecureStore uses the iOS Keychain and Android Keystore. The exact strategy depends on your security requirements and architecture.

12

Interview answers

"Why use an interceptor?"

"An interceptor centralizes authentication logic. Instead of manually attaching the access token to every request and handling 401 responses in every API call, I can use a request interceptor to attach the token and a response interceptor to handle token expiration, refresh the token, and retry the failed request."

"What if 10 requests receive 401 simultaneously?"

"I don't want to send 10 refresh requests. I use a single refresh operation controlled by an isRefreshing flag or promise, and queue the failed requests while the refresh is running. Once the refresh succeeds, I update the token and retry the queued requests. If refresh fails, I reject the queued requests and log the user out."
