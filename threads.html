JavaScript Threads & Event Loop

JavaScript runs one thing at a time, yet it handles timers, network requests and taps all at once. The trick is to separate single-threaded execution from asynchronous work. Get that distinction right and the React Native threading question becomes easy.

02

Is JavaScript single-threaded?

Yes. JavaScript execution is traditionally single-threaded: one JS execution thread has one call stack, and it executes one piece of JavaScript at a time.

🍳

One chef, many timers

A kitchen with one chef can still cook five dishes. The chef starts the oven, sets a timer, and keeps chopping. When a timer rings, the chef deals with it as soon as their hands are free. The chef is the JS thread. The oven and timers are the runtime.

Single-threaded does not mean JavaScript can't handle multiple asynchronous operations. That's where the event loop comes in.

03

JavaScript doesn't block while waiting

timeout.js 
console.log("A");

setTimeout(() => {
  console.log("B");
}, 1000);

console.log("C");

// Output: A, C, B

JavaScript doesn't sit there for one second doing nothing. The timer is tracked outside the call stack, and the callback runs once the timer is done and the stack is empty.

04

The event loop

The important pieces:

Call stack

Where JavaScript runs. One stack, one frame at a time.

Web / Native APIs

Timers, network, sensors. Provided by the browser, or by the React Native runtime and platform.

Queues

Microtasks (promise callbacks) and tasks (timer callbacks, events) wait here.

Event loop

When the stack is empty, it moves the next callback onto it: microtasks first.

In a browser, timers and networking are provided by the browser. In React Native, similar capabilities are provided by the React Native runtime and the platform rather than a browser.

05

Microtasks vs macrotasks

This is extremely important for interviews.

MicrotasksMacrotasks (tasks)
ExamplesPromise.then(), catch, finally, code after await, queueMicrotask()setTimeout(), setInterval(), UI events, network callbacks
When they runAs soon as the current synchronous code finishesOne per turn of the event loop
How many at onceAll of them, until the queue is emptyJust the next one, then microtasks again

The rule: after the current synchronous code finishes, all microtasks are processed before the next task.

order.js 
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

  console.log("C");
});

console.log("D");

⚠️

Microtasks can starve everything else

Because the microtask queue is always emptied completely, a promise chain that keeps queuing new microtasks can hold off timers, events and rendering, just like a long loop would.

06

Blocking the JS thread

One thread means that while a long piece of synchronous code runs, nothing else in JavaScript can: no timers, no promise callbacks, no event handlers. The Blocking the thread example in the visualizer shows a "0 ms" timer waiting 2 seconds.

07

Threads in React Native

React Native has historically been described in terms of multiple execution threads: the JavaScript thread, the UI / main thread, and threads for native modules and other native work.

⚠️

The exact threading model varies with the React Native version and architecture. Don't oversimplify it as "React Native has exactly three threads."

The JavaScript thread

Your JavaScript code generally runs on the JS runtime / thread:

handler.ts 
const handlePress = () => {
  calculateSomething();
  setCount(count + 1);
};
Components

React rendering and component logic.

State

Redux, Zustand and other state logic.

Handlers

Event handlers and JavaScript calculations.

Data

Processing API responses, parsing, sorting.

If you block this thread with expensive synchronous work, your app can become unresponsive:

blocking.ts 
for (let i = 0; i < 10000000000; i++) {
  // expensive work: taps, JS animations and updates all wait
}

The UI / main thread

Native UI operations happen on the platform side:

If the JS thread is heavily blocked, JS-driven interactions become sluggish, even though the native UI thread itself is fine. Native scrolling may still work, but anything that needs JavaScript to respond will wait. This is why React Native performance work often focuses on keeping expensive work off the JS execution path.

✅

Keeping the JS thread free

Run animations on the UI thread (useNativeDriver, Reanimated), avoid needless re-renders (memo, useMemo, useCallback), virtualize long lists, split heavy work into chunks, and move truly heavy computation to native code.

08

The New Architecture changes the communication, not the threading of JS

With JSI, Fabric, TurboModules and Codegen, the communication model is much better than the old Bridge. See the New Architecture for the details.

⚠️

JSI does not make JavaScript multithreaded

That's an important interview point. JSI changes how JS talks to native code. Your JavaScript still runs on the JS thread, one piece at a time.

09

Can JavaScript use multiple threads?

Yes, but not by creating another normal JS thread that shares your variables. Each extra thread gets its own separate JS environment, and they communicate by passing messages.

React Native can use native threads and specialized libraries for background work, and the New Architecture involves native and C++ execution. But don't claim that all React Native JavaScript automatically runs on multiple threads.

10

Interview answers

"If JavaScript is single-threaded, how is it asynchronous?"

"JavaScript execution is single-threaded, but asynchronous operations are handled by the runtime environment. Operations such as timers, networking, and native APIs can be handled outside the JavaScript call stack. When they complete, their callbacks are scheduled, and the event loop executes them when the JavaScript thread is available."

"Does setTimeout create a new thread?"

No. Conceptually:

"Explain threading in React Native."

"JavaScript itself executes on a JavaScript runtime and is generally single-threaded, meaning one JS execution context processes JavaScript work sequentially. React Native also interacts with native platform threads, including the UI/main thread and other native execution contexts. Asynchronous operations don't necessarily block the JS thread because they're handled by the runtime or native platform and their results are scheduled back to JavaScript. In the old architecture, communication relied heavily on the asynchronous Bridge, while the New Architecture uses JSI, Fabric and TurboModules to provide a more efficient interaction model."

One warning

❌

Don't say

"React Native is single-threaded." That's too simplistic.

✅

Say

"JavaScript execution is generally single-threaded, while a React Native application can involve multiple native threads."
